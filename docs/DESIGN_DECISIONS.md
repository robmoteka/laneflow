# Design Decisions

ADR-style log of key syntax and architectural choices made during the
design of LaneFlow v0.1. Each entry records the context, the options
considered, the decision taken, and the reasoning. Entries are numbered
and append-only — superseded entries are marked, not deleted.

---

## DD-001 — Fixed section order (header → direction → lanes → nodes → flows)

**Status:** Accepted, v0.1

**Context:** A document can be parsed in multiple passes or a single
forward pass. Two plausible approaches: (A) require a fixed section order
so a single-pass parser works, or (B) allow sections in any order and
resolve references in a second pass.

**Decision:** Fixed order, validated strictly. Parsers MUST reject documents
with sections out of order.

**Rationale:** LaneFlow is designed to be generated by LLMs. A fixed order
means a generative model can emit sections top-to-bottom without
back-tracking, and a human reader knows exactly where to look for each
kind of declaration. The cost — less flexibility for hand-authors — is low
given that `.laneflow` files are short.

---

## DD-002 — Explicit lane declarations (no lazy lanes)

**Status:** Accepted, v0.1

**Context:** Lanes could be declared explicitly (`lane Sales`) or emerge
implicitly from the first use of a lane prefix (`Sales: ...`).

**Options considered:**
- **Lazy:** shorter files, no declaration ceremony.
- **Explicit (chosen):** lanes appear in a dedicated block; order of
  declaration is the visual order on the diagram.

**Decision:** Explicit only. Using a lane id that was not declared is a
parse error (`LF020`).

**Rationale:** Lazy lanes make ordering non-obvious (visual order would
depend on which node appears first, which is easy to accidentally permute
during edits). They also create a class of silent bugs: a typo in a lane
prefix creates a new lane rather than an error. Explicit declaration
eliminates both problems and keeps the visual layout under the author's
control.

## DD-003 — Node ids are mandatory, separate from labels

**Status:** Accepted, v0.1

**Context:** Three options for node identity:

- **A — Label only.** Nodes are identified by the text of their label;
  the parser auto-generates an internal id. Authors repeat the full label
  when referencing a node in the flow section.
- **B — Optional id.** Authors may add an id prefix to a node; if omitted,
  a hash of the label is used.
- **C — Mandatory id (chosen).** Every node has a short id declared
  alongside its label. The flow section uses ids only.

**Decision:** Option C.

**Rationale:** Option A looks attractive but breaks under the LLM-generation
requirement: if a model generates `[Check availability]` in one place and
`[Check Availability]` (capital A) elsewhere, the parser silently creates
two nodes. Option B is better but creates two syntactic forms, which
increases generation error rates. Option C requires slightly more typing
but makes references unambiguous and the grammar regular. The cost is
acceptable because `.laneflow` files are short and the node-id vocabulary
is small.

## DD-004 — Shape syntax via brackets, not keywords

**Status:** Accepted, v0.1

**Context:** Node types could be declared with a keyword (`task check_avail
"Check availability"`) or inferred from bracket syntax (`check_avail [Check
availability]`).

**Decision:** Bracket syntax, matching BPMN-adjacent convention and
Mermaid's flowchart nodes.

**Rationale:** Bracket syntax is compact and visually communicates the shape
(rounded vs. square vs. diamond). It is already familiar from Mermaid and
similar tools, reducing the learning curve. Keywords would add verbosity
without benefit in a format designed for short files.

The four bracket pairs in v0.1 map to the four most common BPMN shapes:
- `(text)` — event (circle)
- `((text))` — end event (double circle)
- `[text]` — task (rounded rectangle)
- `<text>` — gateway (diamond)

## DD-005 — Single arrow symbol; flow type is derived, not declared

**Status:** Accepted, v0.1

**Context:** BPMN distinguishes sequence flow (within a pool/lane) and
message flow (between pools/lanes) with different visual styles and
semantics. Options for LaneFlow:

- **Two arrow symbols:** e.g. `-->` for sequence, `..>` for message.
- **Single symbol, derived (chosen):** `-->` for both; the parser
  classifies based on whether endpoints share a lane.

**Decision:** Single symbol; the parser derives the type.

**Rationale:** Requiring the author (or LLM) to know which arrow type to use
means they must already know the lane of both endpoints — exactly the kind
of cross-referencing that causes generation errors. Derivation from lane
membership is deterministic, free of author error, and better aligns with
the "one way to write it" principle. Renderers can still visualize the
two types differently.

## DD-006 — Licensing: CC BY 4.0 for specification, MIT reserved for code

**Status:** Accepted, v0.1

**Context:** The repository currently contains only specification documents.
A future parser/renderer will be added.

**Decision:** Specification and documentation → CC BY 4.0. Future code →
MIT (to be added in a separate `LICENSE-CODE` file when the first code
is committed).

**Rationale:** MIT is a software license; applying it to a specification
document is technically legal but semantically awkward. CC BY 4.0 is the
standard open license for documents: it allows free use, distribution,
adaptation, and commercial use, requiring only attribution. This matches
the goal of LaneFlow becoming a widely-adopted, citable standard. The MIT
license will apply to any reference implementation so it integrates cleanly
with the JavaScript/Node ecosystem and compatible projects.

## DD-007 — No escape sequences in labels (v0.1)

**Status:** Accepted, v0.1; revisit for v0.2

**Context:** Labels inside shape brackets may not contain the closing
bracket of their shape. An escape mechanism (e.g. `\]` inside `[...]`)
would remove this constraint.

**Decision:** No escapes in v0.1. The restriction is documented in the spec
and listed as future work.

**Rationale:** Escape sequences complicate the lexer and create edge cases
(what escapes are valid? what happens with `\\`?). In practice, process
step labels very rarely contain bracket characters. Accepting this
limitation in v0.1 keeps the lexer trivially simple. If real-world usage
shows it to be a significant pain point, an escape mechanism can be added
in v0.2 without breaking existing documents.
